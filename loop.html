Anatomy of one loop

One request to the AI coding agent on Surfing Babel, traced through the project owner's diagram of an agent harness, box by box. This is the loop that became pull request #11. It has explicit sub-goals and several real fail-and-retry cycles.

The promptbuild this plan and do a round of error fixing
make clicking off an image take you back to the home page
model calls fail, retry with error context sub-goal / all goals done human review harness and memory traffic
  1. 1
    Prompt

    Three asks in two lines

    "Build this plan" pointed at a document from the previous loop rather than restating it. "A round of error fixing" had no target at all: the harness had to decide what to look for. Only the backdrop click was concrete.

  2. 2
    Context injection from project memory

    What the short prompt was expanded with

    • Code and docs: the repository, and above all docs/search-optimization-plan.md, written in the previous loop. That's what "this plan" meant.
    • The conversation so far: earlier decisions (the 4σ threshold, hourly politeness concerns) and an open observation that all 12 finds came from one test.
    • Measured data on disk: 147 real Babelia frames downloaded earlier for calibration.
    • Session rules: develop on one named branch, commit format, open a pull request and merge.

    No skills or rules files were loaded for this loop. In the diagram's terms, the injection was code, docs and conversation history.

  3. 3
    Planning: goal and sub-goals

    One goal, five tracked sub-goals

    The goal: implement the plan, harden the code, fix the UI ask. It was broken into a written task list before any code was touched:

    1. #1Close the image view on a backdrop click
    2. #2Detection: fix the colour-balance skew, log every score, per-test leaderboards, combined score, fingerprint monitor
    3. #3Throughput: adaptive concurrency, hourly scans, publish every 30 minutes
    4. #4Research spike: Babelia's location → image mapping (time-boxed)
    5. #5Error-fixing round across the codebase

    The plan document had 14 items. Planning chose the ones worth building and skipped five, with reasons. For example, parallel runners would multiply load on Babelia, and the gain from persistent connections was under 5%.

  4. 4
    The model, outside the harness

    Called again at every step

    Each turn, the harness sends the model the prompt plus the full context: the conversation, every tool result so far, the task list. The model replies with its next action. It never edits files or runs commands itself; it asks the harness to, and reads what comes back. That's the two blue arrows: one into planning, one into execution.

  5. 5
    Execution ↔ tools

    The tools that did the work

    Read / Edit / WriteBash + Python curl → Babeliapytestpyflakes Playwright browsergitGitHub API task list

    Long jobs ran in the background while other sub-goals moved forward: an 8-minute recalibration on 1,000 simulated frames, and a live re-score of the site's data against Babelia.

  6. 6
    Result → testing, and the red loop

    Where it failed and retried with the error

    Leaderboards vs. the storage tests 2 failed

    Errorthe image folder held 3 frames more than expected
    RetryRead the error: the new leaderboards correctly keep those frames. The tests' expectation was outdated, so they now compare against everything still referenced.

    The score log 1 failed

    Errorassert (0 == 8): the log was empty
    RetryA real bug: rows missing any test's score were silently dropped. Rows now use a fixed column order, with blanks where a score is missing.

    Live re-score on the real site data unexpected result

    Errorafter the skew fix, none of the 12 finds still reached 4σ
    RetryTreated as a finding, not a crash. It added automatic re-scoring and a reconcile step, then rewrote the site text that still promised "1 in 2,000".

    Static analysis 1 warning

    Errorpyflakes: dictionary key 'description' repeated
    RetryEach demo's hand-written explanation had been silently overwritten. Kept both, under separate names.

    Checks that passed the first time green

    TestedBackdrop click in a browser (closes, clears the address; clicks inside don't close). The publish loop, dry-run against a scratch git remote: 3 chunks, 1 commit. Recalibration: real static max 2.81σ. The research result, against a control: unrelated frames scored 6.25%, which is chance.
  7. 7
    Sub-goal complete → back to planning

    The order sub-goals closed

    #4 research→#2 detection→#1 backdrop+#3 throughput→#5 error fixing

    Each green return re-entered planning with more context than before. The clearest case: the live re-score in #2 changed the plan, so #5's error round also had to cover what happens to old finds when the detector changes.

  8. 8
    All goals done → human review

    One commit, one pull request, then the human

    All five sub-goals closed, so it committed, opened PR #11, merged it and watched the deploy publish. The owner's next message, "improve the demo feature", was the human-review step, and it opened the next loop.

    One difference from the diagram: here the human review came after the merge, not before, because earlier the owner had asked for changes to go straight to main. The next loop added CI on pull requests, so a green check now stands in front of every merge.
